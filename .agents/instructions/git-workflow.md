# Регламент Git-workflow

Этот документ регламентирует ветвление, коммиты, локальное тестирование и слияние изменений в проекте.

---

## 1. Ветвление
* **`main`** — стабильная, всегда собирающаяся ветка. Прямые коммиты кода в `main` запрещены.
* Любая разработка кода ведется в тематических ветках, создаваемых от актуальной `main`:
  * `feature/<agent>-<task-name>` — для разработки функционала.
  * `fix/<agent>-<task-name>` — для исправления багов.
  * `chore/<task-name>` — конфигурации, пакеты, пайплайны.

---

## 2. Формат коммитов
Коммиты делаем небольшими логическими шагами. Описание коммита — на русском языке, тип — на английском:
```
<type>: <краткое описание изменений>
```
**Допустимые типы:**
* `feat` — добавление новой фичи/механики.
* `fix` — исправление багов.
* `docs` — изменения в документации (в `.agents/` или `GDD`).
* `refactor` — переработка структуры кода без изменения поведения.
* `style` — стилистические правки (CSS, форматирование).
* `chore` — конфигурационные файлы, зависимости.

---

## 3. Процесс разработки задачи (Синхронный / Одиночный)

1. **Создание ветки:**
   ```bash
   git checkout main
   git pull
   git checkout -b feature/gemini-my-task
   ```
2. **Написание кода и локальное тестирование:**
   * Перед тестированием убедиться, что проект собирается без ошибок.
3. **Фиксация результатов:**
   * Коммитить небольшими порциями.
4. **Слияние:**
   * Слияние в `main` производится с флагом `--no-ff` (или squash), чтобы сохранить историю фич.
   * После слияния локальная ветка удаляется.
   * Задача на Kanban-доске переносится в `Done`.

---

## 4. Что запрещено
* Коммит секретов и локальных настроек (файлы `.env`, локальные базы данных — должны быть в `.gitignore`).
* Коммит сломанного кода, из-за которого падает сборка.
* Использование `git push --force`.
